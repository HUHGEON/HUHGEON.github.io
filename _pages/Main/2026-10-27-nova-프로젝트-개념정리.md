## 1. JWT vs 세션

> 누구인지는 토큰 서명으로 확인하고, Redis에서는 "끊긴 세션인지"만 확인한다

| 구분 | 세션 | JWT |
|---|---|---|
| 누구인지 확인 | 서버 저장소 조회 | 토큰 서명, 만료 시각 검증 |
| 여러 서버 | 공통 세션 저장소 필요 | 공개 키만 있으면 각자 검증 |
| 강제 로그아웃 | 세션 삭제 | 별도 폐기 장치 필요 |

- **왜 JWT**
  1. **서비스가 여러 개다**: member, catalog, order, preorder, payment, waitingroom이 각자 로그인 여부를 확인한다. JWT는 각 서비스가 공개 키로 직접 검증해서 member를 부를 필요가 없다. 공개 키는 JWKS로 미리 받아 둔다(2번 참고). 세션이면 모든 서비스가 같은 세션 저장소에 붙어야 하고, 세션에 담는 형식까지 서로 맞춰야 한다
  2. **로그인한 사람과 권한은 토큰에서 바로 나온다**: 토큰에 회원 ID와 권한(USER/ADMIN)이 들어 있어서, 인증 필터가 저장소에서 사용자 정보를 꺼내 오지 않아도 요청한 사람과 관리자 여부를 정한다. 이름 같은 다른 정보는 토큰에 없어서 필요하면 member에 묻고, 폐기 여부는 Redis에서 따로 확인한다
  3. **Redis 장애에 덜 흔들린다**: 세션은 Redis가 죽으면 누구인지부터 알 수 없어서 로그인이 필요한 기능이 전부 멈춘다. JWT는 서명으로 신원을 확인하니까 대부분 경로가 계속 동작한다(fail-open). 관리자, 재발급, 내 정보처럼 끊긴 세션이 통과하면 안 되는 곳만 거절한다(fail-closed)
- **대가**: 발급한 토큰을 서버가 바로 끊을 수 없다. 그래서 Redis 블랙리스트를 붙였고, 인증 요청마다 Redis를 한 번 확인한다. "JWT라서 조회가 없다", "완전 무상태다"라고 말하면 틀림
  - 다만 세션은 Redis에서 "누구인지"를 통째로 읽고, 우리는 "끊긴 세션인지"만 작은 키로 확인함
  - 상품 조회 같은 공개 GET은 인증 검사를 아예 건너뛰어서 Redis 조회도 없음
- **세션이 나쁜 건 아님**: Spring Session + Redis로 충분히 운영할 수 있고, 강제 로그아웃은 더 단순함

## 2. 대칭키 vs 비대칭키 (RS256, JWKS)

> 토큰은 member만 만들고, 나머지 서비스는 검증만 한다

- **대칭키(HS512)**: 서명과 검증에 같은 키를 씀. 검증하는 서비스가 토큰도 만들 수 있음. 처음엔 이 방식이라 한 서비스만 털려도 아무 회원 토큰이나 만들 수 있었음
- **비대칭키(RS256)**: 개인 키로 서명, 공개 키로 검증. 공개 키로는 서명할 수 없음
- **적용**: member만 개인 키를 가지고 토큰에 서명함
- **JWKS란**: 공개 키 목록을 JSON으로 공개하는 방식(JSON Web Key Set). 키마다 `kid`라는 이름이 붙음
  1. member가 공개 키 목록을 JWKS로 공개
  2. 다른 서비스가 5분마다 받아 둠
  3. 요청이 오면 토큰 헤더의 `kid`로 맞는 공개 키를 골라 자기 안에서 서명 검증
  - JWKS는 5분마다 미리 받아 두는 것이라, 요청을 처리하는 중에는 member를 부르지 않음
- **왜 JWKS를 썼나**
  - 공개 키를 서비스마다 설정 파일에 박아 두면, 키를 바꿀 때마다 모든 서비스를 다시 배포해야 함. JWKS면 member만 바꾸면 나머지는 5분 안에 따라옴
  - `kid`로 여러 키를 동시에 공개할 수 있어서 서비스를 멈추지 않고 키를 바꿀 수 있음. 새 공개 키를 먼저 공개 → 다른 서비스에 퍼진 뒤 서명 키 교체 → 옛 키로 서명한 토큰이 다 만료되면 옛 공개 키 제거
  - 키 갱신은 뒤에서 따로 돌아서, 모르는 `kid`가 와도 요청이 member 응답을 기다리지 않음

## 3. Access Token과 Refresh Token

> Access는 짧게(30분) API 요청에, Refresh는 길게(14일) 재발급에만 쓴다

| 구분 | Access Token | Refresh Token |
|---|---|---|
| 형태 | JWT | 랜덤 값. DB에는 해시만 |
| 수명 | 30분 | 처음 로그인부터 14일. 재발급해도 안 늘어남 |
| 전달 | `Authorization` 헤더 | HttpOnly, SameSite=Strict 쿠키 |
| 보관 | 프론트 메모리. 새로고침하면 사라짐 | 브라우저 쿠키. 브라우저를 꺼도 남음 |

- **Access 안에 든 것**: 회원 ID(`sub`), 세션 ID(`sid`), 토큰 ID(`jti`), 권한, 만료 시각. 누구나 읽을 수 있어서 개인정보는 넣지 않음. `sid`는 로그인할 때마다 새로 생기고 재발급해도 그대로
- **Refresh를 JWT로 안 만든 이유**: member만 확인해서 안에 정보가 필요 없음. 원문을 저장하지 않으니 DB가 유출돼도 재발급할 수 없음
- **왜 이렇게 나눠 보관하나**
  - Access Token을 localStorage에 두면 자바스크립트로 읽을 수 있어서 XSS가 나면 그대로 털림. 메모리에만 두면 새로고침 때 사라지지만 Refresh 쿠키로 다시 받으면 됨
  - Refresh Token은 HttpOnly 쿠키라 자바스크립트가 못 읽음. 대신 쿠키는 브라우저가 알아서 실어 보내서 CSRF가 걱정인데, SameSite=Strict에 Origin 허용 목록 검사까지 더해 막음
  - 쿠키 경로를 세션 API로 좁혀서, 다른 API 요청에는 Refresh Token이 실리지 않음
- **재발급 시점**: 브라우저가 요청해야만 일어나고, 미리 갱신하는 타이머는 없음
  - 앱을 열거나 새로고침할 때 쿠키로 재발급. 그래서 브라우저를 껐다 켜도 14일 안이면 로그인 유지
  - API가 401을 받으면 재발급하고 원래 요청을 한 번 다시 보냄
- **Rotation**: 재발급할 때마다 Refresh도 교체. 이미 쓴 Refresh가 다시 오면 탈취로 보고 그 로그인 전체를 끊음(재사용 탐지)
  - 왜: Refresh Token은 14일이나 살아서 털리면 오래 악용됨. 한 번 쓰면 바뀌게 해 두면, 털린 쪽과 정상 사용자 중 늦게 온 쪽이 이미 쓴 토큰을 내밀게 되어 탈취를 알아챌 수 있음
  - 30초 유예: 서버는 교체했는데 브라우저가 응답을 버리면(새로고침 연타) 새 쿠키를 못 받음. 그러면 다음 요청에 옛 토큰을 보내서 정상 사용자가 탈취로 찍힘. 그래서 교체 후 30초 안이고 바로 다음 토큰이 아직 안 쓰였을 때만 다시 교체해 줌. 살아 있는 토큰은 항상 하나. Okta 기본값
  - 안 고른 것: 이전 응답을 그대로 다시 주는 방식은 새 토큰 원문을 저장해야 해서, DB에 해시만 둔다는 원칙과 충돌
- **블랙리스트**: 끊을 토큰을 Redis에 적어 두고 요청마다 확인. 토큰(jti) 단위가 아니라 세션(sid) 단위라서 키 하나로 그 세션의 토큰을 전부 막음
  - `auth:revoked-sid:{sid}`: 로그아웃, 동시 로그인, 재사용 탐지에 씀
  - `auth:nbf:{sub}`: 이 시각 전에 발급된 토큰 전부를 막음. 지금은 관리자 전체 폐기에만 씀
  - 요청마다 MGET 한 번으로 두 키를 같이 읽어서, Redis 왕복은 요청당 한 번
  - 로그아웃은 표식을 먼저 심고 Refresh Token을 DB에서 폐기함. 필터가 보는 건 표식이라 Access Token이 바로 막힘
  - 로그아웃 표식은 Access Token 수명(30분)만큼만 둠. 그 뒤엔 토큰이 어차피 만료돼서 막을 게 없음. 표식마다 TTL이 있어서 블랙리스트가 끝없이 쌓이지 않음
  - 회원 계정 제재 기능은 없음(보류)

## 4. 동시 로그인 제한

> 새 기기에서 로그인하면 기존 기기의 연결이 끊긴다

- **왜**: 사전예약은 상품마다 회원당 1건이고 대기열도 상품별이라, 한 계정을 여러 기기에 로그인해 두면 기기마다 다른 상품을 동시에 노릴 수 있었음. 멘토링 의견을 받아 계정당 세션 하나로 제한
- **적용**
  1. 회원 row에 비관적 락(`SELECT ... FOR UPDATE`)을 걸어 같은 회원의 로그인을 줄 세움
  2. 기존 Refresh Token을 전부 폐기하고 새로 발급 (DB)
  3. 기존 `sid`를 Redis 블랙리스트에 기록. 기존 기기의 Access Token도 다음 요청부터 401
- **기존 기기에서 보이는 흐름**: 다음 API 요청이 401 → 프론트가 재발급을 시도 → Refresh Token도 DB에서 폐기돼서 실패 → 로그아웃 상태가 됨
- **DB와 Redis를 같이 쓰는 이유**: DB에서 끊어야 재발급이 막힘. 이미 나간 Access Token은 30분 동안 유효하니 Redis로 막음
- **회원 row를 잠그는 이유**: Refresh row는 첫 로그인 때 잠글 row가 없음. 회원 row는 항상 있음
- **비관적 락 vs 낙관적 락**: 비관적 락은 먼저 잠그고 다른 요청을 기다리게 함. 낙관적 락은 저장할 때 버전이 바뀌었으면 실패시키고 재시도함. 로그인은 두 요청 모두 성공해야 하고 순서만 정하면 돼서 기다리는 쪽이 자연스러움(구조상 설명). 프로젝트 전체에서 `@Version`은 쓰지 않음
- **안 고른 정책**(구조상 설명)
  - 새 로그인 거절: 브라우저만 닫아도 14일 동안 다른 기기에서 로그인할 수 없음
  - 끊을지 물어보기: 확인 단계와 화면이 하나 더 필요함
- **한계**: 여러 계정을 쓰는 건 못 막음. 401에 끊긴 이유를 실어 보내지만, 지금 프론트는 그냥 로그아웃으로 보여 줌

## 5. 캐시: 로컬 vs Redis, 무효화, 스탬피드

> 몇 초 늦어도 되는 건 서버 메모리에, 수정이 바로 보여야 하는 건 Redis에서 버전을 확인한다

| 구분 | 로컬 캐시 (Caffeine) | Redis |
|---|---|---|
| 위치 | 각 서버 메모리 | 모든 서버가 공유 |
| 목록 한 페이지 (로컬 측정) | 0.002ms | 1.05ms (DB는 4.2ms) |
| 수정 반영 | 서버마다 늦게 | 바로 |

- **적용**
  - 로컬: 상품 목록, 카테고리, 랭킹, 홍보 카드
  - Redis + 서버 메모리 사본: 상품 상세, 홍보 본문, 사전예약 회차. Redis에서는 버전만 확인하고 값은 사본에서 읽음
  - Redis: 리뷰
  - 검색어나 필터가 있는 목록은 조합이 끝없어서 캐시하지 않음
- **안 고른 것**: 전부 Redis면 짧은 조회에도 왕복 비용이 들고, 전부 로컬이면 숨김이나 가격 변경이 늦게 보임
- **Redis + 서버 메모리 사본 (2단 캐시)**: Redis 앞에 서버 메모리를 한 겹 더 둔 구조. 기준은 Redis이고, 서버 메모리는 Redis 값의 사본
  - 사본이 생기는 때: DB에서 읽어 Redis에 넣을 때(넣기가 실패해도 남김), Redis에서 값을 읽어 왔을 때
  - 평소: Redis에서는 버전 번호만 GET으로 읽음. 같은 번호의 사본이 있고 TTL의 80%가 안 지났으면 사본으로 답해서, 값을 가져오는 GET과 JSON 변환을 건너뜀. 80%가 지나면 Redis에서 갱신하고 사본도 새 값으로 바꿈
  - 버전 번호는 매번 Redis에서 읽기 때문에, 다른 서버가 수정해서 번호를 올리면 다음 조회부터 옛 사본은 안 씀
  - 상품 상세는 본문만 캐시하고, 회차와 재고 같은 실시간 칸은 요청마다 채움
  - 사본 양은 캐시마다 서버당 JSON 약 4MB 분량까지. 넘으면 Caffeine이 밀어냄
  - 장애 때 이 사본을 쓰는 방식은 6번 참고
- **무효화**: 키를 지우는 대신, 키에 버전 번호를 넣고 데이터가 바뀌면 번호만 올림
  - 키 삭제로는 수정 직전에 읽은 요청이 옛 값을 다시 넣는 걸 못 막음. 조건마다 다른 목록 키를 다 찾아 지울 수도 없음
  - 번호 올리기는 JPA 엔티티 콜백에 걸어 둬서, 쓰기 코드가 늘어도 빠지지 않음
  - 번호는 트랜잭션 커밋 뒤에 올림. 롤백된 수정 때문에 캐시를 비우지 않게
- **스탬피드**: 인기 키가 만료되는 순간 요청이 한꺼번에 DB로 몰리는 현상
  - 같은 키 동시 요청은 서버 안에서 한 번만 DB를 읽고, 나머지는 그 결과를 기다림
  - TTL의 80%가 지나면 기존 값을 주면서 뒤에서 미리 갱신. 운영 부하 시험에서 만료 대기로 0.3~2초 걸린 요청이 계기
  - 분산 락은 Redis 왕복이 늘고 Redis 장애 때 쓸 수 없어서 쓰지 않음

## 6. 장애 대응: 서킷 브레이커, Graceful Degradation, 워밍업

> 빠르게 만드는 거랑 안 죽게 만드는 건 다른 일이더라고요.

- **계기 (10/22 운영 부하 시험)**
  1. 홍보를 오픈하자 홍보 상세 p99가 4초까지 늘었음. 그런데 DB와 Redis 서버는 한가했음
  2. 처음 트래픽을 받은 catalog 서버가 같은 일에 CPU를 2.3~3배 씀. JVM이 아직 덜 데워진 상태
  3. CPU가 밀려 앱이 Redis 응답을 300ms 안에 못 받음. Redis 서버는 멀쩡했지만 앱 입장에서는 장애와 같았음
  4. 실패가 이어져 차단기가 열렸고, 캐시를 건너뛴 요청이 DB와 사전예약 서비스 앞에 줄을 섬
- **문제**
  - 캐시가 빠지는 순간, 캐시가 막고 있던 요청이 원본으로 한꺼번에 감. Redis 문제 하나가 DB와 사전예약 서비스 과부하로 번짐
  - 차단기만으로는 해결되지 않음. 차단기는 "Redis를 부르지 마라"까지만 정하고, 그 요청을 어디로 보낼지는 정하지 않음. 당시에는 차단기가 열리면 DB로 가게 되어 있었음
- **서킷 브레이커**: 실패가 이어지면 일정 시간 호출 자체를 끊음(닫힘 → 열림 → 반열림). Redis 실패가 이어지면 10초 동안 부르지 않아서, 요청마다 300ms를 기다리지 않음
- **Graceful Degradation**: 의존 대상이 장애여도 기능을 조금 낮춰서 핵심은 유지함. 우리 핵심은 상품을 보여 주는 것. Redis를 못 쓸 때 요청이 갈 곳을 순서대로 정함
  1. 서버 메모리 사본으로 먼저 답함(5번의 2단 캐시). 원래 TTL 안이고, 마지막으로 확인한 버전 번호와 같은 사본만 씀. 마지막 확인 뒤 상세는 10분, 사전예약 회차는 1분까지
  2. 사본이 없을 때만 DB를 읽음. 같은 키는 서버 안에서 합쳐 한 번만 읽고, 5초를 넘기면 503
  - 장애 중에 이 서버가 직접 수정한 데이터는 사본을 바로 빼고 안 씀
- **사전예약 서비스가 응답하지 않을 때**도 화면별로 낮추는 수준을 정함

| 화면 | 처리 |
|---|---|
| 목록, 검색 | 마지막으로 받은 회차를 10분까지 사용. 그 뒤엔 사전예약 상품만 제외 |
| 홍보 카드 | 카드는 그대로 두고 시각만 비움 |
| 일반 상품 상세 | 재고 수량만 "모름"(null) |
| 사전예약 상세 | 캐시도 사본도 없으면 503 |
| 관리자 수정, 삭제, 전환 | 회차를 확인 못 하면 거절 |

- **대가**
  - 옛 값이 나갈 수 있음. Redis가 안 되는 동안은 버전 번호를 확인 못 해서, 그 사이 가격 변경이나 숨김이 바로 안 보이고 상세는 최대 10분까지 옛 값이 나감. 못 올린 버전 번호는 기록해 뒀다가 복구 뒤 다시 올림
  - DB로 가는 요청이 0이 되지는 않음. 사본이 없는 상품은 결국 DB로 가고, 합치기로 줄일 뿐
  - 데이터마다 얼마나 낡아도 되는지 정해야 해서 화면별 처리가 복잡해짐
- **왜 이걸 골랐나**: 상품 정보는 몇 분 늦어도 치명적이지 않음. 그래서 조금 낡은 값으로 핵심 기능을 지키면서 원본도 보호함. 다만 데이터마다 낮출 수 있는 한도를 나눔. 상품 상세는 10분 낡아도 되지만 사전예약 회차는 1분까지만 쓰고, 관리자 수정처럼 정확해야 하는 곳은 거절함
- **안 고른 것**
  - 장애 때 전부 DB로: 10/22에 실제로 일어난 일. 과부하가 DB와 사전예약 서비스로 번짐
  - 전부 거절(503): 원본은 지키지만 보여 줄 수 있는 상품 정보까지 사라짐. 커머스에서 상품 페이지가 안 뜨면 그게 곧 장애
- **워밍업**: JVM은 처음 실행하는 코드가 느림(클래스 로딩, JIT). 새 서버는 readiness가 열리기 전, 즉 트래픽을 받기 전에 상세 API를 미리 호출함. 로컬 재현에서 워밍업이 없으면 3번 중 1번 무너졌고, 있으면 한 번도 안 무너짐

## 7. DB 쿼리: 커넥션 풀, 실행 계획

> 쿼리 자체가 빨라도 DB 왕복이 많으면 커넥션 풀이 찬다

- **커넥션 풀**(HikariCP): DB 연결을 미리 만들어 두고 빌려 씀. 연결을 오래 쥐면 다른 요청이 기다림
  - 계기: 운영 부하 시험에서 catalog가 초당 약 130건일 때 p99가 2.4초. SQL 실행은 짧았는데 DB 왕복이 한 번에 수십 ms였음
  - 왜 풀이 찼나: 연결은 마지막 문장이 끝날 때까지 쥐고 있음. 문장 하나하나는 빨라도 문장 수만큼 왕복 시간이 쌓이고, 그동안 다른 요청은 연결을 못 빌리고 기다림
  - 원인: 목록은 건수와 페이지를 두 문장으로 읽었고, 두 문장이 같은 시점을 보게 하려고 REPEATABLE READ 읽기 전용 트랜잭션으로 묶었음. 이 트랜잭션의 준비, 정리용 문장 8개가 쿼리보다 비쌌음
  - 적용: 건수 한 행에 페이지를 `LEFT JOIN LATERAL`로 붙여 한 문장으로 만들고, 트랜잭션은 열지 않음. 한 문장이라 같은 시점을 읽고, 페이지가 비어도 건수 행은 남음
  - `LATERAL`: 조인 오른쪽 서브쿼리가 왼쪽 행의 값을 참조할 수 있게 하는 문법
  - 결과 (요청당 DB 문장 수): 목록 검색 12 → 3, 상품 리뷰 17 → 2, 토큰 재발급 26 → 10
  - 안 고른 것
    - 트랜잭션 없이 두 문장: 사이에 다른 커밋이 끼면 total과 목록이 어긋날 수 있음
    - `COUNT(*) OVER()`: 범위 밖 페이지는 돌아오는 행이 0개라 total을 실을 행도 없음
- **실행 계획**: 옵티마이저가 통계를 보고 인덱스와 조인 순서를 고름
  - 계기: 상품 300개, 옵션 600개를 넣은 직후 통계가 틀려서 상품마다 옵션과 재고 표 전체를 훑음. 목록 조회가 120~143ms였고, 자동 통계 재계산 뒤에도 회복 안 됨
  - 적용: 인덱스 힌트(`FORCE INDEX`, `JOIN_ORDER`, `NO_SEMIJOIN`)로 계획을 고정해 5.6~6.3ms. 통계가 맞을 때(4.5~5.8ms)와 같은 수준
  - 통계를 일부러 틀리게 넣은 테스트로, 고정한 계획이 유지되는지 확인함
  - 안 고른 것: ANALYZE TABLE로도 회복되지만, 데이터를 바꿀 때마다 돌려야 하는 운영 절차가 됨

## 8. 럭키 드로우: 멱등성, Outbox

> 응모를 하나씩 안전하게 보내고, 추첨 전에 건수를 맞춘다

- **멱등성**: 같은 요청을 여러 번 해도 결과가 한 번 한 것과 같은 성질. 재시도나 중복 전달이 있는 곳에 필요
- **Outbox**: DB 저장과 메시지 발행은 한 트랜잭션으로 묶을 수 없음. 그래서 메시지를 같은 트랜잭션 안에서 outbox 테이블에 저장하고, 커밋 후 발행함. 실패하면 다시 발행. 메시지가 두 번 갈 수 있어서 받는 쪽은 멱등해야 함
- **적용**: 크림 방식. 소액 응모비를 받고 정한 인원만 당첨, 떨어져도 환불 없음
  - 결제가 확정될 때마다 응모 한 건씩 Outbox → SQS → worker → 외부 추첨 서버. 멱등 키는 응모 ID, 재시도와 실패 보관은 SQS(DLQ)가 맡음
  - 멱등 키가 필요한 이유: Outbox 릴레이가 다시 보내거나 SQS가 다시 전달하면 같은 응모가 두 번 갈 수 있음. 재시도해도 본문이 같고, 추첨 서버는 응모 ID가 같으면 같은 응모로 봄
  - worker가 성공을 알려 주지 않아서, 추첨 전에 결제 완료 수와 추첨 서버가 받은 수를 비교함(비교는 worker 쪽, 유희준 님)
  - 추첨 시점: 마감 뒤 30초가 지났고 결제 승인 중인 응모가 0건일 때. 30초는 order 서버들 사이 시계 차보다 넉넉하게 잡은 여유. 마감 뒤엔 결제가 새로 시작되지 않아서(승인 직전에 기간을 다시 확인) 이때의 결제 완료 응모가 추첨 대상 전부. 환불이 없으니 늦게 결제된 응모도 반드시 넣어야 함
  - 결제 완료 응모가 당첨 인원 이하면 추첨 없이 전원 당첨
  - 결과 반영은 조건부 UPDATE로 한 번만. 회차 row를 잠그고 전제를 건 UPDATE로 바꿔서, 이미 반영된 회차면 0행이 되어 다시 반영되지 않음
  - 회차 생성과 상품 등록은 Idempotency-Key로 중복을 막음
  - 새 서비스가 아니라 order 안에 둠. 결제, Outbox, 스케줄러를 그대로 쓰려고
- **안 고른 것**
  - 커밋 후 바로 전송: 실패하면 다시 보낼 근거가 남지 않음
  - 마감 때 목록을 한 번에 전송: 큰 호출 하나가 일부만 실패하는 경우를 따로 설계해야 함

## 9. 동시성과 데드락 (장바구니, 재고)

> 락은 모든 곳에서 같은 순서로 잡는다

- **데드락**: 두 트랜잭션이 서로 상대의 락을 기다리며 멈추는 것. MySQL은 둘 중 하나를 실패시킴. 같은 순서로 잠그면 예방됨
- **Lost Update**: 동시에 수정하면 한쪽 수정이 다른 쪽을 덮어쓰는 것
- **적용**
  - 장바구니 주문은 장바구니 → 기존 주문 → 재고 순서로 잠금. 재고는 옵션 ID 순서로 한 번에 잠금. 처음엔 반납과 확보를 따로 정렬해서 순서가 엇갈렸고 데드락이 났음. 그래도 나면 한 번 재시도
    - 예: 주문 A는 옵션 2를 반납한 뒤 옵션 1을 확보하고, 주문 B는 옵션 1, 2를 확보함. 각자 정렬은 했지만 A는 2 → 1, B는 1 → 2 순서로 잠가서 서로를 기다림
    - 해결: 반납과 확보를 옵션별 증감으로 합친 뒤 한 번에 정렬해서 잠금. 정렬 기준도 DB의 바이트 순서로 맞춤. 처음 쓴 `UUID.compareTo`는 부호 있는 비교라 DB 순서와 달랐음
    - 하나라도 재고가 부족하면 앞 주문 취소와 반납까지 전부 롤백
  - 결제 안 된 장바구니 주문은 회원당 하나. 재고를 여러 주문에 나눠 잡아 두지 못하게
  - 다른 서비스 호출은 트랜잭션 밖에서 함. 응답을 기다리는 동안 락을 쥐지 않게
  - 로그인과 로그아웃도 잠그는 순서가 달라 데드락이 났음. 로그인은 회원 row → Refresh Token row 순서인데, 로그아웃은 Refresh Token row를 먼저 잡음. 게다가 외래키 인덱스가 `(customer_id, revoked_at)`이라 `revoked_at`만 고쳐도 외래키 검사가 돌고 회원 row에 공유 락이 걸림. 순서가 반대라 서로를 기다림
    - `performance_schema.data_locks`로 문장별로 잡는 락을 보고 찾음
    - 해결: 재발급, 로그아웃, 전체 폐기도 회원 row를 먼저 잡도록 통일
  - 리뷰, 내 정보 수정은 `FOR UPDATE`로 읽고 고쳐서 Lost Update를 막음. 전에는 리뷰 별점 수정이 그사이 커밋된 본문 수정을 되돌리고, 내 정보 수정 두 개가 칸마다 섞였음

## 10. 이미지 업로드: 브라우저 직접 vs 서버 경유

> 서버가 파일을 직접 받아 저장 전에 검사한다

| 구분 | 브라우저 직접 업로드 | 서버 경유 |
|---|---|---|
| 경로 | 브라우저 → S3 | 브라우저 → 서버 → S3 |
| 서버가 파일을 보나 | 못 봄. 업로드 허가가 담긴 임시 주소(Presigned URL)만 줌 | 봄 |
| 검사 | 올라간 뒤 따로 (Lambda 등) | 저장 전에 |
| 서버 부담 | 없음 | 전송과 메모리 |

비유하면 직접 업로드는 택배 보관함 비밀번호만 알려 주고 물건은 직접 넣게 하는 것이고, 서버 경유는 물건을 받아서 확인한 뒤 넣어 주는 것이다.

- **왜 바꿨나**: 처음 설계는 직접 업로드였고, 프론트가 붙이기 전에 바꿈. 서버가 파일을 못 보니 막을 수 없는 게 많았음
  - 이미지가 아닌 파일
  - 올린 적 없는 주소
  - 같은 주소로 덮어쓰기
  - 안 쓰는 파일 정리
- **Lambda를 안 쓴 이유**: 검사 장치가 필요하다는 건 알았음. 하지만 검사 전 격리, 처리 상태, 실패한 파일 정리까지 새로 만들어야 해서 일정 안에 어려웠음. 그래서 이미 있는 백엔드에서 받아 검사하는 쪽을 택함
- **적용**: 매직 넘버로 형식 확인(확장자는 안 믿음) → 크기 확인 → 재인코딩으로 EXIF 제거 → DB 기록 먼저 → S3. 사진마다 USED/UNUSED를 기록해 두면 정리 배치가 안 쓰는 파일을 지움(배치는 taejoong15 님)
  - 크기는 디코딩 전에 봄. 작은 파일도 디코딩하면 메모리를 많이 쓰기 때문
  - DB 기록을 먼저 하는 이유: 미사용(UNUSED) 기록을 먼저 커밋한 뒤 S3에 올려서, S3에 올라간 파일은 전부 DB에서 추적됨. 순서가 반대면 S3에는 있는데 기록이 없는 파일이 생길 수 있음
- **대가**: 5000×5000 한 장에 약 200MB 메모리가 들어서 서버당 동시 2장까지만 받음. 넘치면 503과 재시도 안내
- **말로 할 때**: "처음엔 브라우저가 S3에 바로 올리는 방식이었는데, 서버가 파일을 못 봐서 이미지가 아닌 파일도 막을 수 없었습니다. 그래서 서버가 받아 검사한 뒤 S3에 올리도록 바꿨습니다."
